# Wisp deployment: Vercel + Render Free

The deployed topology keeps the same application contracts as local development:

- `apps/web` runs on Vercel.
- `apps/api` runs as one Render web service.
- Supabase remains the durable database and authentication provider.
- Upstash remains the rate-limit store.
- Monad Testnet and the checked-in `deployments/10143.json` manifest remain unchanged.

The only runtime difference is `RUN_INDEXER=true` on Render. Render Free does not
support free background workers, so the API process also runs the durable indexer.
Local `pnpm dev` continues to run API and indexer as separate processes.

## 1. Prerequisites

Before creating either deployment:

1. Apply every migration in `supabase/migrations` to the production Supabase project.
2. Enable Email and Google providers in Supabase Auth.
3. Create an Upstash Redis database and copy its REST URL and token.
4. Create a Resend API key. Without a verified domain,
   `onboarding@resend.dev` can send only to the email attached to the Resend account.
5. Keep the existing Monad Testnet deployment manifest and RPC URL.

Generate the two JSON key rings locally. Preserve these values across every
redeploy; changing them makes existing encrypted invite records unreadable.

```bash
printf '{"1":"%s"}\n' "$(openssl rand -hex 32)"
printf '{"1":"%s"}\n' "$(openssl rand -hex 32)"
```

Use one output for `CLAIM_PAYLOAD_ENC_KEYS_JSON` and the other for
`INVITE_STATUS_HMAC_KEYS_JSON`.

## 2. Create the platform projects

In Render, create a Blueprint from this repository and select the root
`render.yaml`. It creates one Singapore-region Free web service using
`apps/api/Dockerfile`. The Blueprint contains only non-secret values and generates
`INDEXER_ADMIN_TOKEN`; it never asks you to paste application secrets. Its first
deploy can fail configuration validation until step 3 syncs the environment.

Use `/health` as the platform health check. `/ready` intentionally returns 503
until Supabase, Redis, RPC, and every indexer cursor are caught up.

Import the same repository in Vercel with these project settings:

- Framework preset: **Next.js**
- Root Directory: `apps/web`
- Include source files outside the Root Directory: **enabled**
- Install command: automatic (`pnpm install`)
- Build command: automatic (`next build`)
- Production branch: `main`

Link the local frontend directory to that project once:

```bash
vercel link --cwd apps/web
```

## 3. Sync every environment variable

The ignored root `.env` is the single source for application credentials. The
sync command validates it, discovers Render's actual public URL, merges all API
variables through Render's API, and upserts all public frontend variables through
the linked Vercel CLI project. Values are sent over stdin/API request bodies and
are not printed or placed in command arguments.

Authenticate the Render CLI once. An API key in the shell or ignored `.env` also
works for CI automation:

```bash
render login
pnpm deploy:env -- \
  --web-origin https://<vercel-production-origin> \
  --create-render \
  --deploy
```

Omit `--create-render` after the first deployment. Use `--render-service <name>`
if the service was renamed. To validate the local values without contacting
either platform:

```bash
pnpm deploy:env -- --dry-run \
  --web-origin https://<vercel-production-origin> \
  --api-origin https://<render-production-origin>
```

No Supabase, Redis, Resend, key-ring, RPC, or frontend variable needs to be
entered individually in either dashboard. `INDEXER_ADMIN_TOKEN` remains the value
generated by Render unless an existing service value already overrides it.

`NEXT_PUBLIC_*` values are embedded during the Vercel build. Redeploy after
changing them; `--deploy` performs that redeploy.

## 4. Update cross-service URLs

Once Vercel assigns the production URL:

1. Pass that exact HTTPS origin to `pnpm deploy:env`; the command sets Render's
   `CORS_ALLOWED_ORIGINS`, discovers `API_ORIGIN`, and sets Vercel's
   `NEXT_PUBLIC_API_URL` together.
2. Run the environment sync command again if either origin changes.
3. In Supabase Authentication → URL Configuration:
   - Site URL: the Vercel production origin.
   - Redirect URL: `https://<vercel-origin>/auth/callback`.
   - Keep `http://localhost:3000/**` only if local authentication is still needed.
4. Confirm Google OAuth still points to Supabase's provider callback:
   `https://<project-ref>.supabase.co/auth/v1/callback`.

Vercel preview URLs are not automatically accepted by the production API because
production CORS is an exact allowlist. Add a stable preview origin explicitly or
use a separate preview backend before testing API flows from previews.

## 5. Verify

The sync command's `--deploy` flag deploys Render first and then Vercel. Render
Free spins down after 15 minutes without inbound traffic, so the first request
after idling can take about a minute. The embedded indexer resumes from its
durable Supabase cursor when the service wakes.

Run the checks against the final origins:

```bash
curl -fsS https://<render-origin>/health
curl -fsS https://<render-origin>/ready
API_URL=https://<render-origin> pnpm smoke:phase2
```

Then verify in a browser:

1. Google and email sign-in return to the Vercel origin.
2. Link the intended Monad Testnet wallet.
3. Send to a registered Wisp recipient and unlock the Inbox.
4. Send to an unregistered handle and open the generated `/c#p=...` claim link.
5. If Resend is configured, test an unregistered email recipient.
6. Claim the note and confirm the explorer transaction.

## Free-tier limitation

Render explicitly positions Free instances for testing and hobby projects, not
production. A sleeping service also pauses the embedded indexer. This topology is
appropriate for the current demo deployment; move the indexer to a paid background
worker and keep the API always-on before treating Wisp as production infrastructure.
